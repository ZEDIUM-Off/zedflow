# Zedflow 0.2.0 — architecture produit et packages de flows

Cette version sépare le moteur Rust, le SDK et les interfaces, et remplace les
nouvelles écritures de flows isolés par des packages explicitement versionnés.
La version produit est `0.2.0`, le protocole client/daemon `2` et l’époque de
stockage `2`. Les formats Rust des flows, bridges et stratégies restent distincts.

## Architecture

Neuf crates sous `rust/` séparent contrats partagés, préparation du contexte,
définitions de flows, compilation pure, stockage, runtime ADK, service
d’exécution, HTTP et CLI. `zf-execution` possède l’admission, les runs et les
sessions indépendamment de HTTP. ADK-Rust 2.2.0, son catalogue et ses pins externes
sont conservés.

`@zedflow/sdk` expose les schémas Zod par domaine, les commandes, les transports,
la synchronisation et les détails à la demande. `@zedflow/vue` fournit les
adaptateurs de lifecycle. Le client et Electron vivent sous `web/apps` ; la
suite navigateur appartient au projet indépendant `e2e/`.

## Flows et conservation

Les nouveaux flows utilisent `.zedflow/flow/<id>/flow.json` et `flow.rs`, avec
inventaire et dépendances locales figées. Les quatre racines de fichiers
historiques restent lisibles ; leur conversion est explicite. Une révision de
package couvre ses assets et dépendances, distinctement du hash exact du Rust
exécuté. Les runs conservent leurs sources historiques. Les exports Cargo
transportent les sources requises et un lock vérifiable hors du dépôt.

La CLI crée des templates de flow, bridge et contexte, valide et compile les
définitions. L’import de la table SQLite historique `compositions` est une
commande hors ligne : sauvegarde cohérente, reçu reprenable et collisions sans
écrasement. La table source et les sessions restent conservées. Voir les
[packages de flows](../development/flow-packages.md) pour la procédure.

Les caches du catalogue et du routage réutilisent les contenus immuables tout
en conservant les validations sémantiques et les barrières de durabilité. Les
fichiers et dépendances actuels restent vérifiés avant admission.

## Mise à jour et retour arrière

Le changement de protocole empêche un ancien client de transmettre un hash de
source là où l’admission attend une révision complète de package. Actualiser le
client avec le daemon ; les données et brouillons ne sont pas une autorisation
de relancer une attente périmée.

Le changement d’époque interdit l’activation à chaud depuis l’époque 1 par le
superviseur : les nouveaux états persistés contiennent des pins de packages que
l’ancien runtime ne sait pas relire. Procéder sans exécution active, arrêter les
writers, puis sauvegarder de façon cohérente les bases et fichiers runtime avant
conversion explicite et démarrage. L’import ne réexécute aucun nœud.

Un retour à l’ancien logiciel après de nouvelles écritures nécessite la
restauration du snapshot complet à l’arrêt. Conserver les anciennes releases et
leurs assets ne remplace pas cette sauvegarde des données. Les lecteurs
historiques permettent au nouveau runtime de consulter et reprendre les données
compatibles ; ils ne rendent pas l’ancien runtime compatible avec les nouvelles.

## Validation et distribution

La qualification de migration a passé 743 tests Rust avec exports Cargo exécutés,
66 tests SDK, 5 tests Vue, 52 tests client, 3 tests superviseur, 99 scénarios navigateur et le
smoke Electron. Les gates associent les résultats aux sources figées ; le ledger
distingue déplacements de tests produit et retrait des expériences du laboratoire.
La qualification de release reprend les commandes dans un clone propre du commit
retenu avant publication des artefacts. Les preuves jointes à la publication
identifient ce commit et les empreintes des fichiers distribués.

La distribution qualifie le daemon Linux sur la cible réellement construite et
le client web. Le smoke Electron Linux ne constitue pas une qualification
macOS/Windows ; aucun installateur universel n’est fourni. Les tests utilisent
fixtures et répertoires temporaires, sans modèle réel ni accès cloud. Aucun
package n’est publié sur npm ou crates.io.

Les commandes complètes sont décrites dans [validation](../validation.md), les
frontières dans [architecture](../architecture/crates.md), et l’exemple multiflow
sous `examples/working-system`.
